# Spec Delta

## Purpose

Populates a development database with a deterministic, realistic Vulpes data set so that developers can manually test every feature of the UI without creating data by hand, while production deployments stay unaffected.

## ADDED Requirements

### Requirement: Seeding is opt-in and development-only
The system SHALL seed data only when the application is started with the `seed` environment active. Without that environment, the system MUST NOT write any seed data and MUST NOT require seeding-related configuration. The production runtime artifact (optimized jar and Docker image) MUST NOT contain the seeding functionality or its data-generation dependencies.

#### Scenario: Start without seed environment
- **WHEN** the backend starts with an empty database and without the `seed` environment
- **THEN** the database contains no projects after startup completes

#### Scenario: Start with seed environment
- **WHEN** the backend starts with an empty database and the `seed` environment active
- **THEN** the seed data set is present before the HTTP API reports the application as started

#### Scenario: Production artifact
- **WHEN** the production Docker image is built
- **THEN** it contains neither the seeding functionality nor the data-generation library

### Requirement: Seeding does not duplicate data
The system SHALL seed only when the database contains no projects. When projects already exist and no reset is requested, the system MUST skip seeding, leave existing data unchanged, and log that seeding was skipped.

#### Scenario: Restart with existing data
- **WHEN** the backend is started a second time with the `seed` environment against the database seeded by the first start
- **THEN** the number of projects and entities is unchanged and a log entry states that seeding was skipped

#### Scenario: Database with user-created data
- **WHEN** the backend starts with the `seed` environment and the database already contains a manually created project
- **THEN** no seed data is added and the manually created project is unchanged

### Requirement: Explicit reset
The system SHALL support a reset option (`vulpes.seed.reset=true`) that, together with the `seed` environment, deletes all Vulpes data (projects and every project-scoped entity with its children) and then seeds the full data set again. The reset option MUST have no effect without the `seed` environment.

#### Scenario: Reset after manual changes
- **WHEN** a tester has modified and deleted seeded records and restarts with the `seed` environment and `vulpes.seed.reset=true`
- **THEN** the database contains exactly the seed data set again and none of the tester's changes

#### Scenario: Reset flag without seed environment
- **WHEN** the backend starts with `vulpes.seed.reset=true` but without the `seed` environment
- **THEN** no data is deleted and no data is seeded

### Requirement: Deterministic data set
The seed data set SHALL be reproducible: two seeding runs with the same configuration MUST produce the same projects and entities with the same keys, names, texts and values, so that testers can refer to specific records in bug reports. Identifiers generated by the database MAY differ between runs.

#### Scenario: Two fresh databases
- **WHEN** two empty databases are seeded with the same configuration
- **THEN** listing items of the project "Eldoria RPG" returns the same keys, names and materials in both

### Requirement: Themed example projects
The seed data set SHALL contain at least two themed projects ("Eldoria RPG" with `labor=false` and "Skyblock Lab" with `labor=true`) whose content resembles real usage. Across these projects, every entity type exposed by the API MUST be represented: items with enchantments, lore lines and flags; fonts with char lines; sound events with file sources; attributes; notifications; and dimension types with attributes and timelines. Minecraft-specific fields (materials, enchantment names, item flags, sound names, dimension resources) MUST use valid Minecraft identifiers or values accepted by the respective API validation.

#### Scenario: Browse a themed item
- **WHEN** a tester opens the items of "Eldoria RPG"
- **THEN** at least one item has a real Minecraft material, one or more enchantments with plausible levels, multiple lore lines and at least one item flag

#### Scenario: Every entity type present
- **WHEN** a tester lists each entity type for the themed projects
- **THEN** every list endpoint returns at least one record, and every parent record with child collections has at least one child in at least one example

#### Scenario: Seeded records pass API validation
- **WHEN** any seeded record is loaded through the API and sent back unchanged via the update endpoint
- **THEN** the update succeeds without a validation error

### Requirement: Project scoping is observable
The themed projects SHALL share at least one entity `key` per entity type so that the separation between projects is visible in the UI.

#### Scenario: Same key in two projects
- **WHEN** a tester opens an item with a shared key in "Eldoria RPG" and in "Skyblock Lab"
- **THEN** the two items are distinct records with different content

### Requirement: Edge-case project
The seed data set SHALL contain a project "Edge Cases" that covers:
- more records than one default API page for every top-level entity type,
- parent records with empty child collections (item without lore, enchantments and flags; font without chars; sound event without file sources; dimension type without attributes and timelines),
- every value of each enum used by the model (environment attribute keys, attribute operators, skybox, cardinal light) at least once,
- numeric fields at their validated minimum and maximum values,
- long texts, Unicode characters and Minecraft `§` formatting codes in text fields,
- ordered child lists (lore lines, font char lines) with enough entries to test reordering,
- unsafe enchantments and enchantment levels above the vanilla maximum.

#### Scenario: Pagination
- **WHEN** a tester lists items of "Edge Cases" with the default page size
- **THEN** the response reports more than one page

#### Scenario: Empty child collections
- **WHEN** a tester opens the seeded item without children in "Edge Cases"
- **THEN** its lore, enchantments and flags are empty lists

#### Scenario: Enum coverage
- **WHEN** the dimension attributes of "Edge Cases" are listed
- **THEN** every environment attribute key and every attribute operator occurs at least once

#### Scenario: Boundary values
- **WHEN** a tester opens the boundary dimension types in "Edge Cases"
- **THEN** each of `minY`, `height`, `coordinateScale` and `monsterSpawnBlockLightLimit` appears at its validated minimum in at least one record and at its validated maximum in at least one record

### Requirement: Empty project
The seed data set SHALL contain one project without any entities so that empty states of all list screens can be tested.

#### Scenario: Empty lists
- **WHEN** a tester opens any entity list of the empty project
- **THEN** the API returns an empty page
